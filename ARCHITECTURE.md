# Arquitetura

## Stack

- **Next.js 16 (App Router) + React 19 + TypeScript** — SSR pra páginas de conteúdo (busca, detalhe de carta) e client components só onde há estado local (coleções, decks, formulários).
- **Tailwind CSS v4** — tokens de design (`src/app/globals.css`) em vez da paleta cinza padrão, pra fugir de cara de template.
- **[TCGdex](https://tcgdex.dev)** (`api.tcgdex.net/v2`) via `fetch` direto, sem SDK — o SDK oficial `@tcgdex/sdk` foi avaliado e removido: seus tipos TypeScript não batem com o formato real da API (o SDK não declara `variants_detailed`/`pricing`, que é onde o preço de mercado realmente vive). Um wrapper fino em `src/lib/tcgdex.ts` com tipos escritos a partir da resposta real da API é mais simples e mais correto.
- **Idioma da API: `en`**, fixo — `pt-br` existe mas cobre ~1.100 das 23.000+ cartas (confirmado em 2026-08-09 via `/v2/pt-br/cards` vs `/v2/en/cards`), insuficiente pra busca geral.
- **Sem banco de dados.** Coleções e decks moram no `localStorage` do navegador (`src/lib/storage.ts`), sincronizados via `useSyncExternalStore` — decisão do fundador: ferramenta pessoal, sem necessidade de login nem sincronizar entre dispositivos.
- **Motion de UI é só CSS** (`transform`/`opacity` + `cubic-bezier`), sem lib de animação — suficiente pra essa superfície de interação (sem drag/gestos que justificassem uma lib de spring física).
- **`tesseract.js`** — única dependência de peso adicionada além do Next/Tailwind, usada só no scanner de câmera (OCR client-side pra ler nome/número da carta). Import dinâmico (`await import("tesseract.js")` dentro de `scanCard.ts`) — nunca entra no bundle inicial, só carrega (e baixa o modelo de idioma via CDN) quando a pessoa realmente aperta o botão de câmera.

## Estrutura de pastas

```
src/
  app/
    page.tsx                 busca de cartas (home)
    card/[id]/page.tsx       detalhe de uma carta (preço, ataques, ações)
    collection/page.tsx      lista de coleções do usuário
    collection/[id]/page.tsx cartas registradas numa coleção
    decks/page.tsx           lista de decks
    decks/[id]/page.tsx      cartas do deck + análise (categoria/tipo/HP/recuo/preço)
    layout.tsx, globals.css  shell + design tokens
  components/                Nav, SearchBox, QuickRegisterSearch, CardThumb, CardActions, QuantityControl, DistBars
  lib/
    tcgdex.ts                cliente da API TCGdex + helpers de imagem/preço
    actions.ts                Server Actions que expõem tcgdex.ts pra client components
    storage.ts                estado local (coleções/decks) sincronizado com localStorage
    deckAnalysis.ts           lógica pura de análise de deck (com self-check em deckAnalysis.test.ts)
    pokedex.ts                dataset estático (1025 espécies, nome + nº nacional) usado nas coleções por geração
```

## Como rodar

```bash
npm install
npm run dev      # http://localhost:3000
npm run build    # build de produção
npm run test     # self-check da lógica de análise de deck
npm run lint
```

Sem `.env` — a API do TCGdex é pública, sem chave.

## Serviços e integrações externas

- **TCGdex** (`api.tcgdex.net`, `assets.tcgdex.net`) — única integração externa. Preço vem de `cardmarket` (EUR) e `tcgplayer` (USD) embutidos na própria resposta da carta; `bestPrice()` prioriza TCGPlayer por ser a fonte mais líquida pro mercado americano, cai pro trend do Cardmarket quando não há.
- **Deploy: Vercel**, conectado ao GitHub (`eudanielhenrique/poketcg`, público) — todo push em `main` gera um novo deploy automaticamente. Produção: https://poketcg-theta.vercel.app

## Decisões arquiteturais não óbvias

- **Coleções por geração já vêm com todos os Pokémon daquela geração listados** (dataset estático em `pokedex.ts`, nomes em inglês vindos da PokeAPI). O usuário não cadastra o Pokémon — só escolhe qual carta/impressão específica tem de cada um. Semeadas uma única vez por navegador (flag `poketcg:collections:seeded` no localStorage), pra não reaparecerem se o usuário apagar todas de propósito.
- **Vínculo espécie ↔ carta registrada é por `dexId`, não por um campo próprio.** Cada carta Pokémon da TCGdex já vem com `dexId: number[]` (a quais Pokémon da Pokédex nacional ela corresponde). Pra saber se o slot "#6 Charizard" está preenchido, cruza-se `collection.cards` (o que foi registrado) contra `card.dexId.includes(6)` — nenhum dado novo persiste no storage além do que já existia (`cards: Record<cardId, qty>`), só a tela de coleção por geração passou a também iterar o dataset fixo de espécies em vez de só as cartas já registradas.
- **Busca reconhece um ID direto da TCGdex antes de cair pra busca por nome** (`looksLikeCardId` em `tcgdex.ts`: tem hífen, tem dígito, sem espaço — ex `base1-4`). Cobre o caso de cartas sem imagem ou com nome repetido em várias edições, onde buscar por nome sozinho não distingue qual carta é qual.
- **Adicionar carta abre um modal de preview em vez de agir direto na grade de busca** (`CardPreviewModal.tsx`). Tanto `collection/[id]` quanto `decks/[id]` passam `onSelect` pro `SearchBox`, que troca o clique-pra-navegar do `CardThumb` por um clique-pra-selecionar; o modal busca o detalhe completo (imagem grande, set, raridade, código, preço) antes de confirmar — resolve a ambiguidade de escolher entre várias cartas parecidas sem imagem.
- **Resultados de busca buscam o detalhe completo de cada carta (`getCard`), não só a lista breve.** A listagem da TCGdex só devolve `id`/`localId`/`name`/`image` — sem set, raridade ou preço, que é o que precisa aparecer pra diferenciar impressões diferentes do mesmo Pokémon. Custo: até 20 chamadas em paralelo por busca (~0.8-1s medido), aceitável com o debounce de 350ms já existente. `MAX_SEARCH_RESULTS` em `tcgdex.ts` controla esse limite.
- **Busca "Nome nº" usa o filtro nativo da API (`?name=X&localId=Y`), não filtragem no cliente.** Tentativa inicial filtrava depois de buscar 20 resultados por nome, o que falhava sempre que a carta certa não estivesse nesses 20 primeiros (nomes populares como "Pikachu" têm centenas de impressões). Combinar os dois filtros na própria query resolve isso — a API já suporta AND entre parâmetros.
- **Fallback de imagem pra pokemontcg.io é melhor-esforço, não uma segunda fonte de dados de verdade.** Quando a carta da TCGdex não tem `image`, tenta buscar a mesma carta pelo mesmo ID na pokemontcg.io (os esquemas de ID coincidem pra boa parte dos sets clássicos) só pra pegar a imagem — nunca mescla os outros campos (preço, raridade etc. continuam sempre da TCGdex). Timeout de 1.5s, nunca lança erro, cai pro verso estilizado se falhar ou não achar. Na prática cobre pouco: os casos de "sem imagem" na TCGdex são majoritariamente Trainer Kits, promoções anuais e edições regionais — exatamente os prints que a pokemontcg.io também não cataloga (seu total de ~20.500 cartas é menor que os 23.500+ da TCGdex). Testado com uma amostra desses casos e a maioria retornou 404 também na pokemontcg.io.
- **Pokédex, Sets e Cartas são ledgers independentes, não visões sobre o mesmo dado.** Registrar uma carta num Set (ex Base Set Blastoise) não a marca automaticamente como "tenho" na Pokédex de Kanto — são perguntas diferentes (`generation`: "tenho pelo menos um Blastoise" vs `setId`: "tenho ESTA impressão do Base Set") e cruzá-las automaticamente exigiria manter um índice global de posse, mais complexo do que o ganho justifica agora. `CardGroup` ganhou `setId?`/`setTotal?` paralelos ao `generation?` já existente — o mesmo tipo serve pros três modos, só a página de detalhe (`collection/[id]`) muda de visão (checklist por `dexId`, checklist por id exato do set, ou grade livre) conforme qual campo está presente.
- **Checklist de Set usa `ChecklistGrid`, componente genérico que substituiu o `PokedexGrid` original.** Roster + estratégia de match (`getSlotKeys`) são injetados pelo caller: Pokédex casa por `dexId` (uma espécie aceita várias cartas diferentes), Set casa pelo `id` exato da carta (um slot só aceita uma impressão específica). Tocar num slot vazio de um Set pré-preenche a busca com o `id` exato (`base1-2`), que já cai no atalho de busca-por-código — resolve sem ambiguidade, ao contrário do slot da Pokédex que preenche com o nome da espécie (aceita qualquer impressão).
- **Scanner de câmera usa OCR (leitura de texto), não reconhecimento visual de imagem.** Comparar a foto contra as ~23k imagens da TCGdex pra identificar a carta exigiria montar e manter um índice de comparação — fora de escopo. Em vez disso, `scanCardText` (tesseract.js) lê o texto impresso na carta, e `guessSearchQuery` extrai uma heurística "Nome nº" dele (regex pro padrão `N/M`, primeira linha que parece nome ignorando rótulos como "Basic Pokémon"/"Stage 2"). O resultado só pré-preenche a busca — nunca busca nem registra sozinho — porque a heurística é imperfeita por natureza (fonte estilizada, ângulo da foto, brilho) e o usuário corrige antes de confirmar.
- **Câmera ao vivo (`CameraLiveModal.tsx`) reusa um único worker do tesseract entre leituras** (`getWorker`/`stopScanner` em `scanCard.ts`) em vez de recriar um a cada frame — o worker é caro de inicializar (baixa o modelo de idioma), recriar a cada ~1.5s tornaria o scan inutilizável. Captura um frame do `<video>` num `<canvas>` oculto, roda OCR nele, e trava o resultado sozinho quando o mesmo "Nome nº" bate duas vezes seguidas (`STABLE_HITS_TO_CONFIRM`) — evita confirmar num falso positivo de um único frame ruim. Se `getUserMedia` falhar (sem permissão, sem câmera), cai automaticamente pro `<input type="file" capture="environment">` de foto única, que já existia e é mais simples/robusto como fallback.
- **Captura recorta só a área do quadro-guia antes de rodar OCR, não o frame inteiro da câmera.** Primeira versão jogava o `<video>` inteiro (fundo, mão, mesa) pro tesseract — a carta ficava pequena demais e cercada de ruído, o que na prática significava nunca reconhecer nada numa foto real (só funcionava com a imagem sintética de teste, sem fundo). A conversão de coordenadas do quadro-guia (posição em tela) pra pixels nativos do vídeo precisa desfazer manualmente a matemática do `object-fit: cover` (o vídeo é escalado e cortado nas bordas pra preencher a tela, então um ponto em tela não corresponde 1:1 a um pixel do sensor) — sem isso o recorte sairia desalinhado. Recorte também amplia 2x antes do OCR (câmera traseira em modo ambiente costuma vir com sensor de resolução baixa por padrão do navegador; pedir `width/height: { ideal: 1920x1080 }` no `getUserMedia` ajuda, a ampliação cobre o resto).
- **Heurística de nome corta por token, não pela linha inteira, dos dois lados.** Foto real gruda lixo do OCR tanto depois do nome ("Dialga lv.45") quanto ANTES ("`: Pumpkaboo`" — reflexo/borda da carta virando um token de pontuação solto, confirmado com print de teste real) — exigir que a linha inteira batesse com o regex de nome (versão original) rejeitava a linha por inteiro nesses casos, quase nunca reconhecendo nada fora do texto sintético de teste. Agora pula token(s) de abertura sem nenhuma letra, depois pega os tokens seguintes que são só letras e para no primeiro com dígito/símbolo — preserva nomes com espaço ("Origin Forme Dialga") e descarta só o lixo colado nas pontas.
- **Cartas com acabamento holográfico/reverse holo continuam difíceis de ler.** O brilho/reflexo diagonal do holo cobre parte do texto na foto (confirmado em teste real — carta holo saiu com OCR majoritariamente ilegível mesmo com recorte e ângulo corretos); sem controle de ângulo/luz na captura isso é uma limitação física, não um bug de heurística. Mitigação futura, se necessário: pedir múltiplos frames e votar a leitura mais comum em vez de confiar num frame só — não implementado ainda, escopo em aberto.
- **Debug visual temporário no `CameraLiveModal`** (miniatura do recorte real + texto bruto do OCR, canto superior esquerdo) — adicionado pra diagnosticar o bug de reconhecimento em foto real sem precisar de acesso remoto ao console do celular. Remover quando o reconhecimento estiver validado como confiável em uso normal.
- **Testado com imagem sintética, não com câmera real** — o ambiente onde isso foi construído não tem uma câmera de verdade pra testar `getUserMedia` fim a fim. A lógica de captura, OCR e o CSS do modal foram verificados (renderiza corretamente, fecha corretamente), mas o comportamento em dispositivo real (foco, iluminação, ângulo) precisa ser validado num celular de verdade.
- **Lista de sets da TCGdex tem 218 no total** (`GET /sets`) — não dá pra mostrar todos de cara sem virar ruído. Sets só aparecem na aba depois que o usuário busca e escolhe um pra acompanhar (`SetPickerModal.tsx`, usa `GET /sets?name=X`); não há auto-detecção de sets a partir de cartas já registradas em outro lugar (ver ponto acima sobre ledgers independentes).
- **"Cartas em destaque" na home é uma lista curada, não um ranking calculado sobre todo o catálogo.** A API do TCGdex só devolve preço no endpoint de detalhe (`getCard`, uma chamada por carta) — calcular "as mais caras de verdade" exigiria buscar as 23k+ cartas uma a uma, inviável. `FEATURED_IDS` em `src/app/page.tsx` é uma lista fixa de 8 clássicos raros conhecidos, escolhida e verificada manualmente (não gerada); a ordenação por preço dentro dessa lista é real (`bestPrice` + `sort`), não é o preço em si que é fake. Não existe dado de "mais procurada" — isso exigiria analytics de busca, que o app não tem (sem backend, sem tracking).
- **`useLocalState` usa `useSyncExternalStore`, não `useState` + `useEffect`.** A primeira versão lia o localStorage num `useEffect` com `setState` — funciona, mas o ESLint (`react-hooks/set-state-in-effect`) sinaliza esse padrão como gerador de re-renders em cascata. `useSyncExternalStore` é a API que o próprio React recomenda pra sincronizar com uma fonte externa mutável (exatamente o caso do localStorage), e resolve o mismatch de hidratação (servidor não tem `window`) sem efeito manual.
- **`Deck` e coleção nomeada compartilham o mesmo shape** (`{ id, name, cards: Record<cardId, qty> }`, tipo genérico `CardGroup`) — mesma estrutura de dados e mesma UI de lista/detalhe pros dois conceitos, só trocando a chave de storage.
- **Preço e detalhes completos exigem uma chamada por carta** (`getCard`), porque a listagem de busca da API só devolve `id`/`name`/`image`. Coleção e deck buscam os detalhes de todas as cartas de uma vez (`getCardsDetailAction`) quando a tela abre.
- **Busca da home (`QuickRegisterSearch.tsx`) auto-arquiva por geração em vez de perguntar a coleção.** A home não tem uma coleção "atual" — diferente de dentro de `/collection/[id]`, onde o alvo já é óbvio e o modal registra ali mesmo. `generationForDexId()` (`pokedex.ts`) mapeia o primeiro `dexId` da carta pra uma das 9 faixas de geração (`GENERATION_RANGES`) e registra direto em `gen-{n}`. Cartas sem `dexId` de geração conhecida (Trainer, Energy, ou promos sem espécie) não têm pra onde ir automaticamente — mostra aviso em vez de arquivar errado ou silenciosamente descartar.
- **Logo do set é capturado uma vez na criação da coleção** (`logo: set.logo` em `selectSet()`, `collection/page.tsx`), não buscado toda vez que a tela abre — mesma URL base da TCGdex (`assets.tcgdex.net/.../logo`, sem extensão) usada com `.png` nos três lugares que exibem (lista de Sets, `SetPickerModal`, header do detalhe). Coleções de Set criadas antes desse campo existir ficam sem logo (mostram placeholder cinza) — não há migração retroativa porque o dado (qual set é) já está em `setId`, só o logo precisaria ser rebuscado, e o app não faz backfill de storage.
